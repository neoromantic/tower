## Кратко для вкладки концепта

Если сохраняем текущий UI, короткая альтернатива — оставить C/SDL2, согласовать окно, буфер, DPR и координаты клика; затем при необходимости отделить zoom башни от размера UI. Это самостоятельная ветка улучшения. Для нового UI/3D рекомендуемая траектория — C/Wasm core → DOM UI + выбранный renderer; полностью модернизировать старые SDL-окна перед этим не требуется. Увеличение разрешения не добавит деталей нынешним спрайтам. Ни одна ветка здесь не реализована и не согласована.

## Разрешение, масштаб и детали — разные задачи

Нужны три независимые величины:

- **Плотность пикселей**: сколько физических пикселей приходится на единицу интерфейса. HiDPI должен повышать чёткость, сохраняя удобный размер кнопок.
- **Масштаб UI**: насколько крупны текст, кнопки и панели. На большом экране интерфейс не должен становиться микроскопическим; на маленьком — просто уменьшаться вместе со всем кадром.
- **Масштаб мира**: сколько этажей и клеток видно. Zoom должен менять башню, сохраняя размер UI; больший viewport может показывать больше мира без изменения игровой сетки.

В [`tower.h`][grid] клетка имеет геометрию 8×36, а содержимое этажа — высоту 24. Эти размеры участвуют в нарезке и композиции спрайтов. Заменять их ради 4K — плохой первый шаг: это уже изменение геометрического контракта. Начальный путь — сохранить мировые единицы, масштабировать представление.

Больший буфер позволяет рисовать больше пикселей, но не создаёт новых деталей в имеющемся sprite sheet. Nearest сохраняет пиксельный рисунок; дробное увеличение может давать неодинаковую толщину пикселей. Сглаживание меняет вид, но не восстанавливает детали. Настоящая детализация потребует новых ресурсов с согласованными pivot, размерами кадров и композициями. Текст следует растрировать в нужной плотности, а не увеличивать уже маленькую текстуру. Целочисленный zoom полезен для нынешнего рисунка, но ограничивает выбор масштаба.

## Альтернативный путь при сохранении текущего UI

### 1. Согласовать окно, буфер и координаты

Первый ограниченный шаг — сохранить логические 960×720 и игровую геометрию, явно согласовать размер буфера с отображением. [SDL2 `SDL_RenderSetLogicalSize`](https://wiki.libsdl.org/SDL2/SDL_RenderSetLogicalSize) задаёт независимое логическое разрешение и масштабирует mouse/touch events окна. При другом aspect ratio сохраняется логическая композиция с полями. Это простой промежуточный результат, но ещё не широкий viewport и не новый UI.

В native различать размер окна и выход renderer через [SDL2 `SDL_GetRendererOutputSize`](https://wiki.libsdl.org/SDL2/SDL_GetRendererOutputSize); high-DPI flag имеет платформенные условия, включая настройку bundle на macOS: [SDL2 `SDL_WindowFlags`](https://wiki.libsdl.org/SDL2/SDL_WindowFlags). Сам flag не решает размер текста.

В web различать CSS-размер и физический буфер canvas. Emscripten предоставляет отдельные функции для них и DPR: [canvas size](https://emscripten.org/docs/api_reference/html5.h.html#c.emscripten_set_canvas_element_size), [CSS size](https://emscripten.org/docs/api_reference/html5.h.html#c.emscripten_get_element_css_size), [device pixel ratio](https://emscripten.org/docs/api_reference/emscripten.h.html#c.emscripten_get_device_pixel_ratio). Размер буфера концептуально следует размеру CSS × DPR; предел плотности выбирается по измерению на целевых устройствах. Не допускать конкуренции CSS/JS и SDL за размер буфера.

Ввод должен преобразовываться ровно один раз. SDL2 logical size уже преобразует события; повторное ручное умножение на DPR даст неверный picking. Для координат, полученных вне этого потока, есть [SDL2 `SDL_RenderWindowToLogical`](https://wiki.libsdl.org/SDL2/SDL_RenderWindowToLogical), начиная с 2.0.18; установленную native-версию здесь не проверяли. DOM overlay сначала определяет, кому принадлежит событие — форме или миру.

### 2. Отделить область мира от UI

После согласования размеров — адаптивный viewport мира, независимый UI scale и zoom. Использовать существующий порядок `render`: преобразование мира охватывает башню, людей, события и ghost, затем UI рисуется в своих координатах. Обновить обратное преобразование, прямые размеры render-прямоугольников, clipping, clamp камеры и minimap вместе. Zoom вокруг точки указателя должен сохранять выбранную клетку под курсором; это требование, а не уже готовая возможность.

Широкий экран отдаёт дополнительное место миру и панелям; узкий — показывает одну основную панель, не уменьшает весь UI до нечитабельного размера. Увеличение шрифта делать вместе с геометрией строк и hit areas: размеры старых диалогов подогнаны под короткие английские подписи. Перерисовать сначала один законченный поток, например выбор инструмента → строительство → информация о комнате, сохраняя существующие команды модели. Не заводить второй набор правил строительства в UI.

Не связывать эту работу с заменой главного цикла. Нынешний frame pacing требует отдельной проверки; более тяжёлый кадр способен замедлить симуляцию. Новые гарантии темпа нельзя обещать по одним исходникам.

### 3. Современные формы и управление

| Вариант | Польза | Цена |
|---|---|---|
| Весь UI остаётся SDL | Одна реализация для native и web, существующие обработчики и визуальный стиль | Layout, фокус, клавиатурная навигация, семантика и доступность требуют своей реализации; пиксельная отрисовка сама их не предоставляет |
| SDL-мир + DOM-панели в web | Обычные кнопки, формы, масштабируемый текст, CSS layout; можно продолжить существующую HTML-оболочку | Появляются граница команд/состояния C↔JS и отдельная native-презентация; нужно согласовать modal, focus, fullscreen и прекращение world input |

Для ветки сохранения текущего UI достаточно адресно исправлять размеры и нужные окна; DOM-инспектор возможен отдельным ограниченным экспериментом. Для нового UI/3D основной путь — выделить C/Wasm core и подключить DOM с выбранным renderer. Это не требует сначала переносить все SDL-окна. В обоих случаях модель остаётся источником истины, UI показывает состояние и отправляет команды; экспорт `ccall` сам по себе не открывает static-функции UI.

DOM не означает автоматическую доступность игры. Для панели нужны подписи, видимый фокус и порядок Tab; для modal — удержание фокуса, Escape и возврат к вызвавшему элементу по [WAI APG](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/). Для самой башни понадобится текстовый способ выбрать этаж/объект и выполнить действие. [HTML Standard о canvas](https://html.spec.whatwg.org/multipage/canvas.html#the-canvas-element) описывает доступное альтернативное содержимое и соответствие интерактивных областей focusable-элементам; одна подпись canvas не заменяет интерфейс объектов.

Клавиатура: сохранить текущие игровые команды, добавить достижимые без мыши действия и не перехватывать их при вводе в DOM-форму. Сейчас [оболочка перехватывает F5 и Ctrl/Cmd+S][keys] по признаку запущенной игры; при новых формах этого признака недостаточно. IME и UTF-8-редактирование обсуждать вместе с существующим ограничением имени и форматом хранения, не обещать локализацию от замены поля ввода.

Touch: эмуляция одиночного mouse event не заменяет interaction design. Нужны явный выбор режима строительства, pan одним пальцем вне размещения, отдельный zoom и подтверждение размещения; убрать зависимость обязательных действий от hover и right click. Жесты, отмена drag и конфликт со скроллом страницы должны иметь одного владельца. Для начала разумнее видимые кнопки pan/zoom и выбор клетки, затем жесты. Touch остаётся непроверенной целью, а не заявленной поддержкой.

## Риски и что останется неизвестным до отдельного прототипа

- HiDPI увеличивает размер буферов и объём отрисовки. Нагрузка на software renderer и браузерный GPU не измерялась; количественных обещаний скорости или сроков нет.
- Возврат web resize может повторить задокументированный дефект размеров. Fullscreen и смена DPR требуют согласованного обновления отображения и ввода, включая выход из fullscreen и перенос окна между дисплеями.
- Не все прямые pixel offsets мира и hit areas просмотрены: это исследование конкретных швов, а не полный аудит 11-тысячной строки `main.c`.
- DOM-панель может пропустить клик в строительство или оставить игру без клавиатурного фокуса. Показ такой панели сам по себе не должен перезапускать session или менять скорость модели.
- Изменение viewport затрагивает не только rendering: Santa получает ширину экрана, camera и minimap считают видимую область. Это проверять адресно, не заявлять полную изоляцию симуляции.
- Ранее выполненный smoke новой графики подтверждает обычное строительство и сохранение, но не HiDPI, touch, screen reader, resize или длинную кампанию. Его нельзя выдавать за проверку этого концепта.

Будущий первый прототип можно считать полезным, когда на обычном и HiDPI-экране после resize/fullscreen совпадают курсор, ghost и выбранная клетка; диалоги читаемы и достижимы; drag не строит сквозь панель; сохранение восстанавливает ту же башню. Затем отдельно проверять широкий viewport, zoom, клавиатуру и touch. Здесь эти проверки не запускались.
