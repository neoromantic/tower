# Четыре направления для Tower

Эксперимент для обсуждения, не изменение движка. Сцены созданы Images 2.6 Flare через явный API model ID `openai/gpt-image-2.6-flare`. Это концепты, не скриншоты работающей игры. Общий размер — 1536×1024, прямой фронтальный разрез, четыре этажа, центральный лифт; сверху вниз: офис/отель, квартира/ресторан, офис/квартира, лобби/кафе. Раскладка задана одним общим префиксом промпта, стилистическая часть различается.

## Сравнение

| Направление | Сцена | Что проверяем | Производство и анимация |
|---|---|---|---|
| Схематичный | [PNG](../../web/experiments/assets/style-schematic.png) | Читаются ли тип комнаты, очередь и заполненность через силуэт и цвет; минимум визуального шума | Простые формы удобно перерисовывать по сетке и менять по состояниям. Генеративный результат мягче строгой векторной схемы; для финального набора нужна единая толщина контуров |
| Современный pixel art | [PNG](../../web/experiments/assets/style-modern-pixel.png) | Сохраняется ли узнаваемость мебели при маленьком этаже и резком масштабировании | Близок существующему контракту sprite sheets. Генерация ещё не гарантирует общую пиксельную сетку, palette и одинаковые силуэты между кадрами; финальные кадры требуют ручной фиксации |
| Тёплый кукольный дом | [PNG](../../web/experiments/assets/style-warm-dollhouse.png) | Даёт ли освещение и цвет помещений жизнь башне без потери обзора | Уют и разнообразие интерьеров; мелкая фактура может исчезать при уменьшении. Разумный принцип — статичные стены и мебель, отдельно люди, двери и свет |
| Стилизованная 3D-миниатюра | [PNG](../../web/experiments/assets/style-miniature-3d.png) | Помогают ли крупные объёмные формы различать комнаты с той же фронтальной камерой | Объём можно запечь в 2D-спрайты. Для серийной анимации постоянная 3D-сцена даёт фиксированную геометрию; один AI-концепт такой сцены не создаёт |

Это проектные выводы о компромиссах, не результаты пользовательского исследования. Победитель не назначен: схема делает акцент на управлении, pixel art — на точной сетке, кукольный дом — на атмосфере, миниатюра — на материальности. Все четыре направления могут оставаться 2D-артом для текущей камеры; 3D-стилизация сама по себе не требует нового движка.

## Масштаб игры и ограничения сравнения

В текущем коде клетка — 8×36, из них 24 px отведены интерьеру: [`CELL_W`, `CELL_H`, `TENANT_H`](https://github.com/neoromantic/tower/blob/8d1f4522d53e57ad781164c1f0d7f2dbe3897227/src/tower.h#L27). Ширины комнат различаются: офис 72 px, single hotel 32 px, ресторан 192 px — [`ITEM_WIDTH`](https://github.com/neoromantic/tower/blob/8d1f4522d53e57ad781164c1f0d7f2dbe3897227/src/tower.h#L71). Концепты намеренно показывают общий одинаковый состав помещений, а не точную сетку существующего save.

Увеличенный концепт не доказывает читаемость на 24 px. При выборе стоит смотреть и полную сцену, и уменьшение: сначала видны этаж/шахта/тип комнаты, затем очередь и занятость; детали стола вторичны. Промпт задаёт одинаковые координаты, но независимые генерации не гарантируют совпадение пиксель в пиксель. Уменьшение помогает обсуждать читаемость, но не заменяет финальную нарезку ресурсов.

## Движение

[Исходный sprite sheet](../../web/experiments/assets/elevator-loop-sheet.png) — одна сгенерированная PNG, шесть последовательных видов площадки в сетке 3×2. [GIF](../../web/experiments/assets/elevator-loop.gif) — детерминированная сборка этих ячеек; это не сгенерированный видеопоток. Предмет демонстрации — открытие и закрытие дверей, фиксированная камера и неподвижный человек. Качество регистрации и перехода следует оценивать отдельно от привлекательности одного кадра.

Текущий renderer выбирает прямоугольник из texture: [`render_occupants`](https://github.com/neoromantic/tower/blob/8d1f4522d53e57ad781164c1f0d7f2dbe3897227/src/main.c#L3599) использует кадры 16×24; [`render_shaft`](https://github.com/neoromantic/tower/blob/8d1f4522d53e57ad781164c1f0d7f2dbe3897227/src/main.c#L3849) выбирает кадр кабины по заполненности. Для интерьера берётся горизонтальный кадр [`frame_idx * frame_w_hint`](https://github.com/neoromantic/tower/blob/8d1f4522d53e57ad781164c1f0d7f2dbe3897227/src/main.c#L1936). Поэтому GIF — демонстрационный формат; движку нужны подготовленные sprite sheets нужной геометрии и состояний. Экспериментальный лист 3×2 не является готовой заменой существующего ресурса. Изменений C/SDL, упаковки ресурсов или таймингов здесь нет.

Лист проверен визуально: последовательность открытия и закрытия дверей читается, человек и площадка в целом сохраняются. Есть небольшое дрожание регистрации/форм между ячейками; это пригодная демонстрация идеи, но не готовая production-анимация. GIF содержит ровно 6 кадров 512×512 по 180 ms, бесконечный loop; палитра общая для кадров. Все четыре сцены также просмотрены: типы помещений и камера совпадают по смыслу, точные границы и число предметов различаются. Схематичный вариант получил мягкую иллюстративную фактуру; pixel-вариант не следует считать проверенным атласом с единой целочисленной сеткой.

## Источники и происхождение

[Анонс OpenAI, 4 ноября 2026](https://openai.com/index/introducing-images-2-6/) подтверждает семейство Images 2.6 Flare/Sunburst и показывает GIF-примеры с шестью кадрами в сетке 3×2. [Карточка модели](https://developers.openai.com/api/docs/models/gpt-image-2.6-flare) задаёт точный ID `gpt-image-2.6-flare`; [руководство](https://developers.openai.com/api/docs/guides/image-generation) описывает поддержку GIF в Image API. Здесь запрошена PNG-сетка и GIF собран локально: поддержка native GIF не выдается за использованный режим.

[Официальная документация Vercel](https://vercel.com/docs/ai-gateway/modalities/image-generation/openai) описывает `/v1/images/generations` для image-only моделей. Выбранный ID присутствовал в [каталоге Gateway](https://ai-gateway.vercel.sh/v1/models). Прямой OpenAI API с доступным ключом не видел обе 2.6-модели (HTTP 404); Gateway позволил явно выбрать Flare. Встроенный imagegen не раскрывает ID, а доступный Figma tool предлагал 2.5; они не использовались.

Точные промпты, параметры, время, request/response metadata, подтверждение маршрута модели и SHA-256 — [provenance.json](../../web/experiments/assets/provenance.json). Поля модели отражают ответ шлюза о маршрутизации, а не независимую аттестацию весов. Секретов в метаданных нет. Существующая генерация art из основного проекта не использована как источник новых изображений. Бенчмарки и оценки сроков не проводились.
